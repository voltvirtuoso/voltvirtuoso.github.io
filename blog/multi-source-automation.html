Designing automation that can choose a power source

How I decided which power source should win in my ESP32 home automation project, and why the local controller keeps the final say.

Aug 03, 20267 min readBy Haroon Raza
AutomationPowerESP32

When a system can draw from grid power, solar, and a backup generator, “turn it on” is not a complete control strategy. The useful engineering work is deciding which source should win, what to do when information is incomplete, and how to make every transition understandable.

My intelligent multi-source home automation project used an ESP32 to coordinate WAPDA grid, solar, and backup-generator sources. It combined automatic failover, CT-based load monitoring, DHT22 sensing, Firebase Realtime Database, and a mobile interface. The project was a useful reminder that the problem is not only switching: it is turning a set of competing conditions into a safe operating policy.

Start with a policy, not hardware wiring

Before drawing the switching diagram, write the source policy in ordinary language. In this project, the intended priority was solar, then grid, then generator. That is concise, but it still needs rules. What does “available” mean? How long must a source be stable before it is selected? What happens if two inputs disagree? When should the generator start rather than wait?

A policy can be expressed as a state machine rather than a scattered set of if statements. Each state has a current source, an allowed next source, entry checks, and a reason for its transition. That makes it easier to test the logic and to explain it to someone looking at the system later.

// Conceptual source-selection order
if solar_is_healthy: use solar
else if grid_is_healthy: use grid
else: request generator start

// But only after confirming stability and safe switching conditions.
Rule of thumb

“Source present” and “source safe to select” are different signals. Good failover logic leaves space between detecting a signal and committing a load to it.

Measure enough to make the decision credible

CT-based load monitoring across the three sources gave the project a way to see more than source availability. Load information supports better decisions: it can show whether a source is carrying demand, reveal unexpected changes, and make switching behaviour easier to interpret. The DHT22 measurements were useful for environmental visibility and could also support conditional appliance behaviour, such as turning on a fan at a thermal threshold.

There is an important distinction here. Telemetry is not the same as control. A mobile app can make the system more visible, but the local controller should remain able to protect the physical system if the network goes away. The cloud interface should report and request; the local logic should still own the time-sensitive safety choices.

Build boundaries around transitions

Multi-source systems need guardrails because switching has consequences. In any power-control design, the exact hardware protection and electrical isolation approach must be designed and reviewed for the specific installation. At the firmware level, the same attitude means defining boundaries:

  • Do not switch based on a single noisy sample.
  • Use a confirmation window before declaring a source healthy or failed.
  • Record the reason for a transition so it can be diagnosed later.
  • Separate manual requests from automatic safety actions.
  • Expose a clear current mode: automatic, manual override, waiting, or fault.

Automatic generator start within seconds of dual-source failure was one goal of the project. But speed only helps when the transition rules are clear. A hasty system can produce rapid switching; a well-designed one switches once and stays switched.

Make the mobile interface reflect the system, not hide it

The MIT App Inventor interface connected through Firebase Realtime Database provided live temperature and humidity graphs, generator and pump status, and remote control of four or more appliances. That user-facing layer becomes more useful when it reflects the controller’s actual state instead of simply showing the latest button press.

Useful interface elements include the active source, last transition reason, sensor freshness, control mode, and any outstanding fault. These small pieces of context reduce the temptation to make blind remote decisions. They turn the app from a remote switch panel into a window into the automation system.

Summary

The hard part of this project was not the ESP32, Firebase or the CT sensors. It was deciding the priority order, how long a source has to be stable before I trust it, and what the system does when it is unsure. Once those rules were written down, the code was straightforward.
