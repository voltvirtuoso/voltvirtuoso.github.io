Reliable ESP32 automation starts with state

What an ESP32 should save, check and report when it restarts, based on what I learned using NVS and SPIFFS at CMGL.

An ESP32 that reconnects to Wi-Fi after a reboot is not necessarily reliable. The more important question is whether it returns to a safe, intelligible operating state, and whether the person using it can tell what happened.

During embedded systems work, I used ESP32 NVS and SPIFFS to keep calibration data, user settings, and web content available after reboots. That experience made a simple point clearer: persistence is part of the system design, not a later convenience feature. When a device controls something physical, restarting without context can be just as risky as disconnecting.

State is more than a saved value

It helps to separate three kinds of state. First is configuration: settings a user or technician expects to survive, such as thresholds, device names, calibration constants, and network details. Second is operating context: information that helps the firmware decide how to re-enter the workflow after a reset. Third is safety state: the conditions that should default to a known mode until the device has verified its inputs and outputs.

Not every value deserves permanent storage. Writing too often increases wear and can preserve noise rather than meaning. A better approach is to store changes when they represent an intentional checkpoint: a user saves a setting, calibration completes successfully, or a configuration version is updated.

Worth asking

If power disappears at the least convenient moment, what must the device remember, what must it re-check, and what must it refuse to assume?

Design a boot sequence, not a reboot

A reliable startup sequence should be visible in the design. That does not mean a complicated framework. It means deciding what happens before control is enabled. One useful mental model is:

// The control path should earn its way back to action.
load known configuration
validate configuration version and ranges
read current sensors and output feedback
select a safe default state
connect to services without blocking control logic
publish a fresh status snapshot
enable automatic behaviour only after checks pass

The important detail is that connectivity does not automatically grant permission to act. A control system may be able to reconnect long before its sensor values are credible. By separating those steps, the device can tell a clearer story: “I am online, I have restored settings, I am waiting for stable input,” rather than silently behaving as if nothing happened.

Use the storage layer for the right job

On ESP32 projects, NVS is a natural fit for small key-value settings such as calibration points, flags, and user preferences. A filesystem such as SPIFFS can suit larger web assets or structured data that needs file-like handling. The right choice depends on the data shape, but the design questions are the same:

  • What is the source of truth for this value?
  • How will an older saved format be recognized after the firmware changes?
  • What happens when a value is missing, out of range, or partially written?
  • Can the system boot into a safe, recoverable mode without it?

Versioning is especially helpful. A small configuration version allows the firmware to migrate a known older structure, set safe defaults when it cannot, and make the change visible in the status output. That is much easier to troubleshoot than an unexplained reset to factory behaviour.

Report status accurately

Persistent state can create a false sense of certainty if it is not paired with current observation. A saved tank threshold is useful; it is not a current water-level reading. A saved output preference is useful; it is not proof that a relay is physically responding. Good telemetry labels those differences clearly.

For a connected automation system, I prefer a small status snapshot that includes configuration health, sensor freshness, network state, last command, and current control mode. Even a simple web page or MQTT topic becomes more useful when it answers the practical question: is the device safe to trust right now?

Summary

Most of this is unglamorous: a sensible default, a checked input, a saved calibration value, a clear status message. None of it shows up in a demo, but it decides whether the device still makes sense after the first restart and the first power cut.
