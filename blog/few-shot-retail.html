Few-shot detection is a product decision, not just a model

Why our Smart Cart uses barcodes first and few-shot vision second, and what that did to the design.

Jun 29, 20266 min readBy Haroon Raza
AI / dataRetailSystems

On this page

A model can be impressive and still be the wrong first decision. In retail systems, the useful question is not “can vision recognize every item?” but “what mix of signals gives the customer and operator the most reliable result for the least unnecessary complexity?”

In a collaborative Smart Cart ML module, barcode scanning was treated as the primary item-detection path. Few-shot object detection, a Raspberry Pi 5 touch interface, a RAG-based chatbot, Dockerized services, and a Django admin dashboard added capability around that simple foundation. The key product lesson was to let machine learning solve the parts that actually need machine learning.

Barcode first is a systems choice

Barcode scanning is fast, low-cost, and already associated with a structured product identifier. It avoids asking a vision model to infer an identity that the product can often state directly. For a practical cart experience, this reduces the computational load and lowers the chance of confusing visually similar products.

That does not make computer vision irrelevant. It changes its role. Vision can help where a barcode is unavailable, an item is unusual, or an extra confidence signal improves the user experience. The result is a layered system rather than a single model expected to solve every interaction.

Design rule

Use the most dependable low-friction signal as the default. Introduce an advanced model where it closes a real gap, not simply because it is technically available.

Where few-shot detection fits

Few-shot object detection is attractive when new product types must be introduced without collecting a large labelled dataset. In the Smart Cart module, the target was to extend detection using fewer than five training samples per item. That is valuable for product turnover, but it should be evaluated as an operational workflow, not only as an accuracy number.

Questions worth asking include: Who captures the initial samples? What background variation is needed? How is a new class validated before it appears for customers? What happens when confidence is low? A model that learns quickly is useful only if the surrounding process makes that speed trustworthy.

The interface is part of the model’s outcome

The Raspberry Pi 5 touch interface was intended to show cart contents and personalised recommendations in real time. This is where detection results become a product interaction. A customer should not have to interpret a confidence score or debug a model assumption. The interface should show a clear item identity, give a way to correct it, and preserve trust when the system is uncertain.

The RAG-based chatbot followed the same principle. It retrieves contextual product information to support the shopper, but the value depends on whether the answers are grounded in the right catalogue information and presented at the right moment.

Plan for the operator too

The project also included Dockerized services and a Django admin dashboard for sales trends and customer behaviour. These pieces matter because a system is not complete when the customer sees it. Someone needs to update products, examine trends, identify failures, and understand whether the deployed experience is doing useful work.

  • Containerization helps make services more consistent across development and deployment environments.
  • An admin view can turn anonymous usage into a clearer operating picture.
  • Low-power optimization keeps the hardware constraints visible as the feature set grows.
  • A correction path is essential when item detection is uncertain or wrong.

Summary

Few-shot detection is useful, especially when the product range keeps changing. But the bigger lesson was in the design: pair the model with simple, dependable signals, show the user when the system is unsure, and build the tools the store operator needs around it.
