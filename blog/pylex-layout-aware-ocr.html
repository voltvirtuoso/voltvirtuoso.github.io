When OCR correctness is also a coordinate problem

Lessons from Pylex on rotated PDFs, dense technical drawings, inference runtimes, and the difference between detecting text and placing it usefully.

OCR is often described as a recognition problem: find the characters and return the words. For searchable documents, that is only half the job. The words must also land in the right place, with the right orientation, without making the page that people see any worse.

Pylex is an open-source Python OCR and document-extraction toolkit built around that distinction. It accepts images and PDFs, adds an invisible searchable text layer, and keeps the original visible page intact. The project became most interesting when the difficult inputs were not ordinary paragraphs but rotated pages, engineering drawings, symbols, and small labels near line-art.

The overlay problem

A simple pipeline can render a page, run OCR, and paste text back on top. That sounds reasonable until a PDF carries a /Rotate value. The OCR image may be in the orientation a viewer displays, while the PDF content stream still uses a different coordinate system. A text layer can then be technically present but visibly misplaced when selected, searched, or copied.

The practical fix is to make orientation explicit before merging the overlay. Pylex renders the page as the viewer sees it, transfers the page rotation into the content stream, and anchors each OCR line at the start of its detected polygon rather than its centre. Geometry is not a cosmetic post-processing step; it is part of correctness.

Design principle

Preserve the source page as the visual truth. Add searchability around it instead of reconstructing the document from OCR output.

Dense documents need local resolution

Technical drawings create a different failure mode. A small label in an open area may survive a whole-page resize, while the same label inside a crowded symbol cluster can disappear. Line-art, mixed text scales, vertical labels, and patch boundaries all make one global pass a fragile assumption.

Pylex uses overlapping tiles for large or dense pages, maps detections back into page coordinates, and de-duplicates overlaps. It also applies a targeted 90-degree retry to likely vertical candidates. This is deliberately narrower than rotating every image: the extra work is spent where the document suggests it may recover useful text.

Runtime is part of the user experience

OCR performance is not only about the model. Importing the engine, compiling a backend, downloading weights, rendering pages, and writing the final PDF all shape how the command feels. A terminal that appears stuck at zero percent is a reliability problem even when the inference eventually succeeds.

Pylex makes initialization, page rendering, tile inference, and output construction visible in its progress reporting. The automatic CPU path can select OpenVINO when available, then standard ONNX Runtime, with dynamic Paddle as a fallback. In the project’s directional local benchmark, dynamic Paddle took about 10.29 seconds on an equivalent 1845 × 832 image, compared with roughly 0.81–0.95 seconds for standard ONNX Runtime and 1.06 seconds for OpenVINO. Those numbers are useful for choosing what to measure next, not promises for every machine.

Batching honestly

Parallelism is another place where a useful abstraction needs a clear boundary. Pylex runs independent files in separate worker processes, with each worker reusing its own OCR engine. That avoids unsafe concurrent calls on one engine and prevents the model from being rebuilt for every file. It does not make the pages inside one PDF run in parallel; the unit of parallel work is the file.

This distinction keeps the command’s performance story honest. More workers can improve throughput for a folder, but they also consume memory and repeat engine startup. GPU users should be especially careful: several workers sharing one GPU may contend for memory instead of improving throughput.

The takeaway

The strongest lesson from Pylex is that document intelligence lives between several layers: recognition, coordinate systems, file formats, runtime behaviour, and validation. A searchable PDF is successful when the text can be found, selected, and copied without disturbing the page a person trusts.

For production use, the next meaningful step is a representative validation set: rotated pages, crowded drawings, low-resolution scans, and ordinary office documents, measured for both accuracy and end-to-end runtime. Configuration helps, but evidence from the target documents should decide which profile is reliable.
