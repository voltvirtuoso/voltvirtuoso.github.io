Treating a VoIP lab like a deployable service

What my VoIP internship at GOMARKHO taught me about making a FreeSWITCH setup easy to rebuild and easy to check.

Jul 24, 20265 min readBy Haroon Raza
VoIPDeliveryLinux

On this page

A lab can work perfectly once and still be difficult to operate. A deployable service is different: it can be set up again, checked again, and understood by someone who was not present for the original configuration.

During a VoIP engineering internship, I worked with FreeSWITCH functionality, Docker, CI/CD pipelines on AWS, Bash automation, and Linux-based VoIP servers. The main lesson was transferable well beyond telephony: operational consistency is a feature, and it begins before the project becomes complicated.

Repeatability is the first reliability feature

VoIP systems combine several moving pieces: service processes, routing rules, credentials, ports, storage, monitoring, and network conditions. Manually rebuilding a working environment can easily turn into a collection of undocumented steps. Containers help reduce that drift by making the service definition, dependencies, and runtime assumptions more explicit.

Docker does not remove the need to understand the system. It does, however, make it easier to ask useful questions: Which ports should be exposed? Which files must persist? What environment variables are required? What happens when a process restarts? Answers written in a container definition are easier to review than answers remembered by one person.

Quick test

If a teammate had to rebuild the service next week, could they do it from a documented repository and a small set of declared inputs?

Small checks prevent larger surprises

I also used Bash scripting for server setup and disk monitoring. These are not glamorous tasks, but they have direct operational value. A service that fills its disk, loses access to a necessary file, or quietly stops reporting its condition does not care whether the original configuration was elegant.

A useful health check does not need to be sophisticated. It should answer a practical question early enough for someone to act. For example:

# Conceptual monitoring checklist
check service process is running
check configured ports are listening
check disk has safe free capacity
check logs are updating
check backup or configuration files are present

What matters is the habit of defining a known-good state. Without it, monitoring becomes a pile of numbers. With it, monitoring becomes a prompt for a human decision.

CI/CD is a conversation between change and confidence

A CI/CD pipeline can be described as automation, but its deeper role is consistency. It creates a predictable path from a change in the code or configuration to a built, reviewed, and deployable artefact. Even simple pipelines make it easier to notice when a change has not been tested, packaged, or documented.

For infrastructure-adjacent work, I think the most valuable pipeline behaviours are often modest: validate configuration, build the image, label the artefact, deploy to the intended environment, and leave a clear record of what changed. The point is not to automate every decision. The point is to make routine decisions repeatable so attention can remain on the exceptional ones.

Why this matters in VoIP

Telephony has an immediate user-facing consequence: a broken route or unavailable session can mean a call that does not connect. FreeSWITCH routing and session-management work therefore benefits from the same discipline as embedded control: make the expected path visible, define behaviour around failure, and make the running state easy to inspect.

That mindset makes VoIP feel less like a specialised world and more like another engineering system. The inputs are signalling and configuration rather than a sensor, the outputs are calls rather than a relay, but the reliability questions remain familiar.

Summary

Most of the work was removing things that only I knew. Containers, scripts, disk checks and CI/CD made the setup easy to reproduce, and made it obvious when something stopped working.
