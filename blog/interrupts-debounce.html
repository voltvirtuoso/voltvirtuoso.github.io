A button is a control problem

Debouncing and interrupts on a PIC16F877A microwave simulator, and why one button press should only count once.

Jun 14, 20264 min readBy Haroon Raza
FirmwareInputsEmbedded

A push button is not a clean digital event. It is a physical component with contacts that bounce, timing that varies, and a human on the other side who expects one press to mean one action. Treating it as a control problem makes embedded interfaces much more dependable.

During an embedded systems internship, I built a PIC16F877A microwave simulator with LCD feedback and keypad input. Applying debouncing and interrupt handling helped improve input accuracy in a time-sensitive interaction. The project made an enduring point: seemingly small input details can decide whether an interface feels reliable or random.

Why the first signal is not always the real signal

Mechanical contacts do not generally move from open to closed in one perfect transition. They can make and break contact several times over a short interval. A microcontroller sampling fast enough may see that as a burst of presses. If each edge triggers an action, a user who pressed once may move through several menu items, add several seconds to a timer, or start and stop a process unexpectedly.

Debouncing is the decision to wait for evidence that an input is stable before accepting it as intentional. The exact timing depends on the hardware and interaction, but the goal stays the same: turn a noisy physical signal into one clear event.

Question to ask

What evidence does the firmware require before it believes a human action happened, and what does it do while it is waiting for that evidence?

Two common ways to debounce

A simple approach is to detect a change, wait a short interval, then check whether the input remains in the expected state. Another is to sample the input periodically and accept a new state only after it has remained consistent across several samples. Both can work when they are designed around the rest of the control loop.

// Conceptual stable-sample method
if input_state == previous_sample:
    stable_count += 1
else:
    stable_count = 0

if stable_count > threshold and input_state != accepted_state:
    accepted_state = input_state
    handle_intentional_event()

The implementation must also account for whether a press or a release should create the event. Many interfaces feel more predictable when the action occurs on a confirmed press and the button must be released before a new press is accepted.

Interrupts are useful when they lead somewhere clear

Interrupts can help the microcontroller respond promptly to a relevant input or timing event. But an interrupt service routine should remain short and deliberate. Heavy display updates, lengthy delays, or complex decisions inside the interrupt can make the rest of the firmware harder to reason about.

One useful pattern is to let the interrupt capture that an event may have happened, then let the main application logic validate the event and update the system state. This keeps the immediate response fast without moving the whole application into interrupt context.

Feedback closes the loop for the user

The microwave simulator included LCD feedback and keypad interaction. Visual feedback matters because it confirms the system understood the user. If a user presses a key and the display immediately reflects the expected input, the interaction feels stable. If the display lags, repeats, or changes unexpectedly, the technical cause may be bounce or timing, but the human experience is simply mistrust.

That is why input handling belongs with the broader control design. The input is a sensor for human intent; the display is an actuator for user confidence; and the firmware should connect them with clear, observable state changes.

Summary

A debounce window, a short interrupt routine, a clear rule for when a press counts and an immediate display update are all small decisions. Together they make the difference between a button that works and one that feels random.
